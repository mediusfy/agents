## Infrastructure Review: Hermes/OpenClaw Platform Audit

Drew completed a deep review of the Hermes + OpenClaw deployment architecture. The report is attached to this session in WebChat (as a media file).

### Key Findings — Risk: HIGH

**Critical (fix immediately):**
- Plaintext live secrets across Helm values, docs, scripts, JSON config — rotate all affected credentials
- Public unauthenticated Hermes exposure via hermes.drewjocham.com
- Tailscale serve bypass path also unauthenticated
- Two overlapping Kubernetes Secret resources both named `hermes-secrets`

**High (fix soon):**
- No NetworkPolicies — SaaS workloads and agent workloads not isolated
- No resource quotas on any namespace
- RWO PVCs + single replicas + spot-node assumptions = reliability risk for Honcho/pgvector
- Shared memory (Honcho) is conceptually right but operationally fragile

**Medium:**
- Deployment ownership fragmented between Helmfile, Makefiles, and ArgoCD
- Ingress for Hermes needs lockdown
- Stale K3s docs and inconsistent architecture naming (Hermes vs older conventions)
- Mixed naming conventions across Hermes, hermes, Hermes and secrets, Secrets

### Recommended migration order
1. Rotate secrets → move to SOPS or External Secrets
2. Lock down Hermes ingress + remove Tailscale public bypass
3. Make shared memory a first-class platform service (durable storage, clear GKS/local access)
4. Enforce SaaS-first isolation (namespaces, NetworkPolicies, quotas, RBAC, node pools)
5. Consolidate deployment under pure GitOps
6. Clean stale docs, rename consistently around Hermes
