## Executive summary

Rufkis is not a toy repo. The review found a much more mature system than the top-level documentation suggests: there is real multi-tenant data modeling, hardened Kubernetes work in places, a substantial Vue control plane, CI/CD, Helm, Terraform, observability components, load-test code, API governance code, and a backend with meaningful auth and AI plumbing. The project is, however, currently in a dangerous middle state: some foundations are production-grade, while several launch-blocking seams are either insecure, inconsistent, undocumented, or disconnected from the product promise.

The core product direction is strong: a SaaS control plane where developers, SREs, and managers can monitor clusters, validate alerts with an AI agent, run API and load tests, reduce context switching, and see what the agent is doing in a discreet but trustworthy way. The current repo partially supports that vision, but the highest-risk gaps are in tenant isolation, agent privileges, unauthenticated surfaces, observability correctness, docs/onboarding, and transparency of agent actions.

Overall recommendation: proceed, but only after a focused stabilization milestone. Do not add major product surface area until the Phase 0 blockers below are fixed.

## High-level verdict

- **Product fit:** promising, but uneven. The control plane and load-test UX are good seeds. The transparent agent activity model is not yet backed by an audit-grade action log.
- **Architecture maturity:** better than the docs imply. The app has moved beyond some older planning docs, including multi-tenant RLS work and service facades, but the architectural record is stale.
- **Security posture:** high risk for SaaS. Tenant isolation is single-layered and the single layer is currently bypassable in realistic deployment conditions.
- **Operational readiness:** not ready for production monitoring SaaS. Prometheus scrapes the wrong port, alert rules are missing, and several Helm/Kubernetes hardening controls are incomplete.
- **Frontend/UX:** structurally strong, but accessibility and consistency need focused work. The UI has excellent patterns, but they are applied inconsistently.
- **Documentation/DX:** currently a blocker. The README is effectively empty, `CODING_STANDARDS.md` is missing, `CODE_STYLE.md` is empty, and build prerequisites are buried in CI comments.

## What is already worth keeping

- **Backend hardening patterns:** the main backend has deny-by-default CORS, constant-time token comparison in some paths, a reflective RPC method allowlist, circuit breakers, bounded AI worker-pool behavior, and a mature `.golangci.yml`.
- **Tenant model intent:** the RLS policy migration is well structured and fail-closed in policy text. The enforcement layer is the problem, not the whole model.
- **Helm and cloud security foundations:** several charts use strong `securityContext` settings, resources, non-root intent, read-only root filesystems, and capability dropping.
- **GCP posture:** GKE Workload Identity, private cluster work, pinned Terraform modules, GCS state, cosign keyless signing, SBOM generation, and policy-controller/Kyverno style admission policies are all good foundations.
- **Frontend architecture:** the Vue control plane has a clean registry-driven IA, Pinia state, robust real-time plumbing, bounded buffers, spam guards, polling cleanup, DOMPurify-sanitized markdown, and a strong load-test form pattern.
- **Crypto and SQL hygiene:** session tokens are hashed, password hashing uses bcrypt, DB config encryption uses AES-256-GCM, SQL is parameterized, and shell execution uses arg slices rather than shell strings.

## Blocking issues

### Tenant isolation is bypassable

**Severity:** Critical
**Primary area:** security, database, architecture

The SaaS multi-tenant boundary depends almost entirely on Postgres RLS. The RLS policies are good, but the enforcement model is broken in three ways:

- `014_enable_rls.up.sql` enables RLS but does not `FORCE ROW LEVEL SECURITY`.
- The app appears to connect as the table owner role, so Postgres can silently bypass RLS for that role.
- `SetOrgID` uses `set_config(..., false)`, which is session-scoped, and there is no verified pool reset hook. Behind PgBouncer transaction pooling, this can leak an org context between tenants.

This is the top launch blocker. A multi-tenant SaaS cannot expose cloud credentials, DB connection configs, incidents, user activity, and cluster data while relying on a bypassable isolation layer.

**Required fixes:**

- Add `ALTER TABLE ... FORCE ROW LEVEL SECURITY` for every tenant-scoped table.
- Split migration owner and runtime app roles. Runtime must be non-owner, `NOSUPERUSER`, and `NOBYPASSRLS`.
- Change org context to transaction-local: `set_config('rufkis.org_id', $1, true)` or `SET LOCAL` inside explicit transactions.
- Add explicit `org_id` filtering in application store methods as defense-in-depth.
- Add regression tests that run as the runtime app role and prove cross-org reads return zero rows.

### Agent RBAC can read all Kubernetes Secrets

**Severity:** Critical
**Primary area:** security, SRE, customer trust

The in-cluster agent has cluster-wide read permissions on `secrets` via the Helm ClusterRole. Because the agent connects back to the SaaS, this creates a direct path for customer secret exfiltration if Rufkis, the tunnel, or the agent is compromised.

**Required fixes:**

- Remove cluster-wide `secrets` `get/list/watch`.
- Use namespaced `Role` and `RoleBinding` only where there is an explicit, documented use case.
- Prefer secret metadata or health signals over secret value access.
- Add a public least-privilege RBAC contract to the agent docs.

### Cloud Run services are publicly invokable

**Severity:** Critical
**Primary area:** cloud security, GCP-first posture

Terraform grants Cloud Run invoker to `allUsers` and configures broad ingress. This conflicts directly with a SaaS handling cluster telemetry, cloud accounts, and alerting workflows.

**Required fixes:**

- Remove `allUsers` invoker.
- Put Cloud Run behind authenticated ingress, IAP, Cloud Run IAM, API Gateway, or a load balancer with Cloud Armor.
- Set ingress to internal plus load-balancing where appropriate.
- Ensure every service fails closed when auth configuration is missing.

### Prometheus scrapes the wrong backend port

**Severity:** Critical
**Primary area:** observability, product credibility

Prometheus targets `backend:9090`, but backend metrics are served on the API router listening on `:8080`. In the shipped compose stack, the product cannot observe its own backend metrics.

**Required fixes:**

- Change the scrape target to `backend:8080`.
- Add a Helm `ServiceMonitor` or equivalent production scrape config.
- Add at least baseline alert rules for scrape health, request error rate, latency, worker saturation, queue depth, and agent disconnect rate.

### The product lacks an audit-grade agent action log

**Severity:** Blocking for product promise
**Primary area:** architecture, UX, trust, compliance

The product promise is that Rufkis validates alerts, tells the user what it is doing, and provides a discreet way to observe the agent's actions and thinking. The current repo has partial user-activity and Kubernetes audit logging, but not a durable, user-visible, event-sourced agent activity stream.

**Required fixes:**

- Define an `agent_activity` or `agent_timeline` domain model.
- Record tool calls, observations, decisions, confidence, proposed actions, human approvals, denied actions, and final outcomes.
- Persist immutable entries with tenant/org scoping and trace IDs.
- Stream summarized activity to the UI with progressive disclosure.
- Explicitly separate "thinking summary" from raw hidden chain-of-thought. Show useful reasoning summaries, evidence, and next actions, not private model internals.

### AI alert validation is currently misleading

**Severity:** High to blocking for product credibility
**Primary area:** backend, AI product, UX

The backend review found an "AI analysis" loop that returns hardcoded/fabricated results after a fake delay. For a product whose differentiator is alert validation, this is dangerous because it creates user trust before real verification exists.

**Required fixes:**

- Rename fake analysis paths to demo/mock mode and hard-gate them outside production.
- Make real analysis explicit: inputs, model/provider, tools used, confidence, evidence, and failure modes.
- Persist analysis provenance in the agent activity log.
- Add tests that production config cannot use fake analysis.

### Alert ingress is unauthenticated and unbounded

**Severity:** High/blocking
**Primary area:** security, cost control, reliability

The alert-ingress webhook can accept spoofed alerts and create Pub/Sub or processing cost DoS if exposed.

**Required fixes:**

- Require signed webhook auth or tenant-scoped API keys.
- Apply request size limits, rate limits, idempotency keys, and replay protection.
- Use a bounded queue and explicit backpressure behavior.

### api-gov auth can fail open

**Severity:** High
**Primary area:** authentication

The api-gov middleware skips auth if the API key is blank. A missing secret should not turn a control plane into a public API.

**Required fixes:**

- Fail closed at startup when required auth secrets are missing.
- Use constant-time token comparison.
- Prefer scoped, rotatable, per-tenant credentials over a single global static key.

## Product and architecture alignment

### Where the repo aligns with the SaaS vision

- **Cluster monitoring:** there is Kubernetes-oriented backend, agent, Helm, observability, topology, and monitoring code.
- **Load and API testing:** there are load-test and broker pieces, and the frontend load-test form is one of the strongest UX patterns in the repo.
- **SaaS control plane:** there are org/workspace concepts, OAuth/workspace integration plans, Cloud Run/Terraform/Helm deployment paths, and multi-tenant RLS work.
- **GCP-first:** the infra strongly favors GKE, Workload Identity, GCS state, Cloud Run, and Google IAM patterns.
- **AI-first direction:** the backend has AI components and worker-pool/circuit-breaker thinking.

### Where the repo is off track

- **Google/AI priority is inconsistent:** infrastructure is GCP-first, but LLM integration appears DeepSeek-first, with Vertex AI and GCS only stubbed or incomplete.
- **Eventing is aspirational:** the product needs a clear event spine for alerts, agent actions, audit logs, notifications, and UI state. Broker/eventing decisions are not fully wired.
- **Transparent agent UX is shallow:** the UI can show that something is happening, but not enough of what Rufkis did, why, what evidence it used, and what it will do next.
- **Docs understate and misrepresent maturity:** older context claims some items are missing that now exist, while current blockers are not visible from the front door.
- **Security model is too single-layered:** RLS is strong as a backstop, but not safe as the only tenant boundary.

## Frontend and UX findings

### Strengths

- Registry-driven IA is a good fit for a product that must unify clusters, alerts, load tests, APIs, SaaS integrations, and AI workflows.
- The load-test form is a strong model for accessible, testable, user-friendly enterprise UI.
- Optimistic chat with error rollback, DOMPurify-sanitized markdown, bounded real-time buffers, and polling cleanup show thoughtful engineering.
- Shared components such as `StatusRibbon`, `EmptyState`, and `DiagnosedError` are good patterns.

### UX blockers

- Keyboard accessibility is inconsistent. The review found many clickable `div` and `span` elements, and the primary sidebar navigation is keyboard-inoperable.
- Focus states are not globally reliable. A focus color token exists, but focus styling is applied only in a small part of the UI.
- Toast notifications are silent to screen readers because they lack appropriate live-region semantics.
- Theming is inconsistent. Thousands of hardcoded hex colors undermine the token system and break light/dark behavior.
- Loading, empty, and error states are fragmented. Good shared components exist but are used in too few places.
- Motion is overused. Many infinite animations lack `prefers-reduced-motion` guards.
- Agent transparency is too shallow. Users see "investigating" but not a trustworthy activity timeline.

### UX direction to restore trust

Build the product around a "control with confidence" model:

- Show a compact agent activity ribbon for every ongoing investigation.
- Let users expand into a timeline: trigger, data fetched, checks run, anomalies found, confidence, recommendation, proposed action, human decision.
- Make every agent action reversible or approval-gated when mutating.
- Use severity-aware copy: "observed", "suspected", "confirmed", "action proposed", "action taken".
- Give managers a high-level incident narrative, while giving SREs raw evidence and trace links.

## Infrastructure, SRE, and database findings

### Critical and high-priority infra issues

- Prometheus is misconfigured and cannot scrape the backend metrics.
- `api-gov/k8s/30-secrets.yaml` defines both a plain Secret and an ExternalSecret with the same target name, ships unsubstituted placeholders, and disables Postgres TLS.
- No PodDisruptionBudgets are present.
- Startup probes are missing.
- NetworkPolicies are disabled by default.
- "GitOps" is currently imperative `helm upgrade` from CI, not Argo CD or Flux.
- There are no Prometheus alerting rules.
- The agent Dockerfile lacks a non-root `USER` while the chart enforces `runAsNonRoot`.
- Stateful Terraform resources lack `prevent_destroy`.
- Several tenant tables filtered by RLS do not have `org_id` indexes, including high-volume activity tables.

### Database direction

RLS is the right baseline for this product, but it must become a defense-in-depth layer instead of the only isolation layer.

Recommended database work:

- Add `FORCE ROW LEVEL SECURITY` and split owner/runtime roles.
- Add application-layer `org_id` filters.
- Add tenant indexes, especially `(org_id, ts DESC)` for `user_activity`.
- Normalize timestamp handling to `TIMESTAMPTZ`.
- Add `updated_at` triggers where currently left to client code.
- Add tests that prove no tenant can fetch another tenant's cloud account, DB connection, incident, alert, or activity log by ID.

## Security findings by theme

### Broken access control

- RLS bypass risk.
- No app-layer org scoping in key stores.
- MCP tools need caller auth and org scoping before SaaS exposure.
- Agent ClusterRole is too broad.
- Public Cloud Run surfaces.

### Credential handling

- Cloud credential JSON is stored as plaintext text unless reference-only usage is enforced.
- DB URLs use `sslmode=disable` in Kubernetes manifests.
- Grafana defaults to a known admin password in compose.
- Some rendered manifests include API keys directly.

### SSRF and outbound request safety

The product must call user-configured or tenant-configured endpoints: Prometheus, Jira, OIDC issuers, LLM base URLs, load-test targets, and API-test targets. That is a core SaaS capability, but it requires a shared SSRF-safe HTTP client.

Required design:

- Allow only `https` for tenant-supplied external URLs unless explicitly approved for private agents.
- Block loopback, link-local, RFC1918, metadata IP ranges, and DNS rebinding.
- Re-check resolved IPs at dial time.
- Apply this safe client everywhere, including runners.

### AI and prompt injection

Alert text, pod names, log lines, runbook content, and third-party ticket data are untrusted input. The current human-approval seam reduces risk, but it must become an architectural invariant.

Rules to encode:

- LLM output must never directly mutate Kubernetes, cloud, tickets, or notifications without explicit policy and approval.
- Untrusted content must be delimited and labeled in prompts.
- Tool execution must use allowlisted operations and tenant/org-scoped credentials.
- Every tool call must be logged in the agent activity timeline.

## Proposed ADRs

### ADR: Tenant isolation model

**Decision:** Use layered tenant isolation: application-layer `org_id` checks, Postgres RLS with `FORCE ROW LEVEL SECURITY`, separate migration/runtime roles, and transaction-local tenant context.

**Why:** A single control failure must not cause cross-tenant data exposure.

**Consequences:**

- Every tenant-scoped store method receives org context.
- Tests must prove cross-org IDOR attempts fail.
- Migration and runtime credentials differ.
- PgBouncer transaction pooling is supported safely.

### ADR: Agent activity event stream

**Decision:** Every agent investigation emits immutable, tenant-scoped activity events with trace IDs and user-visible summaries.

**Why:** Transparency is a core product differentiator and a trust requirement for AI-assisted SRE workflows.

**Consequences:**

- UI streams compact activity updates.
- Long-form activity timeline is available per alert, test, and cluster investigation.
- Mutating actions require approval and are logged.
- Raw private model reasoning is not exposed. Evidence, tool calls, and reasoning summaries are exposed.

### ADR: GCP-first AI provider strategy

**Decision needed:** either commit to Vertex AI/Gemini as first-class provider or reposition AI provider support as pluggable with DeepSeek as an initial adapter.

**Why:** The product strategy says Google and AI are first-class and GCP has priority, but the implementation appears DeepSeek-first.

**Consequences:**

- If GCP-first: prioritize Vertex AI adapter, Google IAM auth, GCS trace/artifact storage, and Cloud Logging/Trace integration.
- If provider-neutral: define provider interface, safety contract, eval harness, cost controls, and tenant-level provider configuration.

### ADR: Safe outbound networking

**Decision:** All tenant-supplied outbound calls use a shared SSRF-safe client and policy layer.

**Why:** Monitoring, API testing, OIDC, integrations, and load testing all require outbound calls. That makes SSRF a core product risk, not an edge case.

**Consequences:**

- Central allow/deny policy.
- Metadata and internal IP protections.
- Audit log entries for outbound attempts.
- Private target testing requires an in-cluster or customer-side runner with scoped egress policy.

## Recovery roadmap

### Phase 0: stop-the-bleeding fixes

**Goal:** make the repo safe enough to keep developing as a SaaS.

1. Fix tenant isolation — `FORCE ROW LEVEL SECURITY`, non-owner runtime role, transaction-local org GUC, app-layer `org_id` filters, cross-tenant regression tests.
2. Remove dangerous public/auth surfaces — remove Cloud Run `allUsers`, make api-gov and runner auth fail closed, add constant-time compares, authenticate alert ingress.
3. Lock down the agent — remove cluster-wide secret reads, remove broad hostPath mounts unless explicitly needed, add least-privilege RBAC docs.
4. Fix observability basics — Prometheus scrape target, ServiceMonitor, basic alert rules.
5. Remove fake AI from production — make mock analysis demo-only, add provenance to real analysis output.

### Phase 1: restore product trust

**Goal:** make Rufkis feel transparent, reliable, and controllable.

1. Implement the agent activity event model.
2. Stream activity to the UI with compact and expanded views.
3. Add human approval records for mutating actions.
4. Add incident/alert timeline views for SREs and manager summaries.
5. Standardize loading, empty, error, and diagnosed states.
6. Fix keyboard navigation, focus rings, aria-live toasts, reduced motion, and clickable non-button elements.

### Phase 2: production hardening

**Goal:** make the deployed system resilient and auditable.

1. Enable NetworkPolicies by default.
2. Add PDBs, startup probes, topology spread constraints, and custom-metric HPAs.
3. Replace imperative CI deploys with Argo CD or Flux.
4. Add Trivy, gosec, govulncheck, npm audit, and gitleaks/trufflehog to CI.
5. Pin third-party actions and linters.
6. Add `prevent_destroy` to stateful Terraform resources.
7. Encrypt or reference-only store cloud credentials.
8. Enable DB TLS through PgBouncer/Postgres.

### Phase 3: documentation and DX reset

**Goal:** make the repo understandable for developers, SREs, and future AI agents.

1. Write a real README and quick start.
2. Restore/create `CODING_STANDARDS.md`.
3. Move `.context.md` content into maintained architecture docs.
4. Create operator runbooks.
5. Document load testing, API testing, agent activity, tenant isolation, and cloud integration patterns.
6. Update ADRs to reflect what is already implemented and what has changed.

### Phase 4: strategic product expansion

**Goal:** expand only after the trust foundation is solid.

1. Decide and implement the GCP-first AI provider strategy.
2. Add Vertex AI/Gemini integration if GCP-first remains a product priority.
3. Build SaaS integrations through a scoped connector framework.
4. Add API anomaly detection tied to the same activity/event model.
5. Add multi-cloud adapters for AWS and DigitalOcean after the GCP path is complete and safe.

## Suggested immediate implementation order

If you want to put the repo back on track quickly, start with these PRs:

1. **PR 1: Documentation and standards anchor** — Add `CODING_STANDARDS.md`, replace empty README with quick start and architecture, add `docs/architecture.md`. This helps every later code change stay consistent.

2. **PR 2: Tenant isolation hardening** — Add RLS force migration, add runtime DB role separation, change org GUC to transaction-local, add explicit `org_id` filters and tests.

3. **PR 3: SaaS edge auth lockdown** — Remove public Cloud Run invoker, make api-gov auth fail closed, authenticate alert ingress, add rate limits and request limits.

4. **PR 4: Agent least privilege** — Remove secret reads, review hostPath usage, add agent RBAC contract docs, add install-time permission explanation.

5. **PR 5: Observability baseline** — Fix Prometheus scrape, add ServiceMonitor, add alert rules, add dashboards for Rufkis itself.

6. **PR 6: Agent activity timeline MVP** — Add event schema, persist activity entries, stream to UI, add a compact activity ribbon and expandable timeline.

7. **PR 7: Accessibility and UI consistency pass** — Replace clickable div/span controls, add global focus styles, fix toast live regions, apply tokenized colors, respect reduced motion.

## Final recommendation

Rufkis should not be treated as a rewrite candidate. The repo has enough real foundation to recover. The right move is a stabilization milestone that tightens security, observability, and product trust before expanding the AI and integration surface.

The biggest mindset shift should be: Rufkis is not just a monitoring UI. It is a trusted operational co-worker. That means tenant isolation, least-privilege agents, audit-grade activity logs, safe outbound networking, and accessible transparent UX are product features, not compliance chores.
