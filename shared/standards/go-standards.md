# OpenClaw Coding Standards — Single Source of Truth

These standards apply to **all Go services** generated by the openclaw agent ecosystem.

---

## 1. Go Code Standards

### 1.1 Language & Toolchain
- **Go version**: 1.25+ (match toolchain in `go.mod` with Dockerfile build image)
- **Formatting**: `gofmt` (tabs, no trailing whitespace). Run `gofmt -w .` before committing.
- **Line length**: 100–120 characters maximum.

### 1.2 Import Ordering
Exactly **three groups**, separated by a blank line, alphabetized within each group:

```go
import (
    "context"
    "fmt"
    "log/slog"

    "github.com/go-chi/chi/v5"
    "go.opentelemetry.io/otel/attribute"

    "dev.azure.com/schwarzit-wiking/.../internal/config"
    "dev.azure.com/schwarzit-wiking/.../internal/service"
)
```
1. Standard library
2. Third-party
3. Local monorepo packages

### 1.3 Naming Conventions
| Element | Convention | Example |
|---------|-----------|---------|
| Exported types/funcs | PascalCase | `ProcessRequest`, `NewService` |
| Unexported | camelCase | `publisher`, `filterConfig` |
| Constants (exported) | PascalCase | `ResultSuccess` |
| Constants (unexported) | camelCase | `logKeyError`, `traceSpanName` |
| Error sentinels | `Err` prefix + PascalCase | `ErrMessageFiltered`, `ErrPublishFailed` |
| Log keys | `logKey` prefix + PascalCase | `logKeyMessageID`, `logKeyCorrelationID` |
| Trace keys | `trace` prefix + snake_case | `traceAttrMessageID`, `traceSpanSolacePublish` |
| Packages | lowercase, one word, matches directory | `config`, `metrics`, `solace` |
| Interfaces | named after behavior + `er` suffix | `SolacePublisher`, `ArchivePublisher`, `MetricCollector` |
| Use `any` | Not `interface{}` | Go 1.18+ style |

### 1.4 File & Package Structure
```
cmd/<service>/main.go           # Entry point, signal handling, errgroup orchestration
pkg/app.go                      # Composition root / dependency injection assembly
internal/
  config/                       # Configuration structs, env loading
  api/                          # HTTP server, router, middleware
  apperrors/                    # Custom error types, disposition system
  handlers/                     # Handler interface + concrete handlers
  handlers/model/               # Request/response data models
  handlers/<domain>/            # Domain-specific handler implementations
  service/                      # Core business logic
  service/filter/               # Business rule validation
  service/model/                # Domain model builders
  metrics/                      # OpenTelemetry instruments
  subscriptions/                # Handler registry / routing
```

### 1.5 Error Handling
- **Sentinel errors**: defined as `const` with typed `Error` string type:
  ```go
  type Error string
  func (e Error) Error() string { return string(e) }
  const (
      ErrMessageFiltered  Error = "message filtered out"
      ErrPublishFailed    Error = "failed to publish message"
  )
  ```
- **Wrapping**: always wrap with context using `fmt.Errorf`:
  ```go
  fmt.Errorf(errFmtWrapper, ErrMessageCreation, buildErr)  // "%w: %v"
  ```
- **Matching**: always use `errors.Is` — never raw `==` on wrapped errors.
- **Disposition pattern** (for event-driven services): errors carry retry semantics:
  ```go
  apperrors.Mark(err, apperrors.Ack)        // 200 OK, ack the message
  apperrors.Mark(err, apperrors.BadRequest)  // 400, non-retryable
  apperrors.Mark(err, apperrors.Retry)       // 500, triggers retry
  ```
  Implemented via a `dispositionError` wrapper implementing `DispositionError` interface with `Disposition()`, `Unwrap()`, and `Error()`.

### 1.6 Logging
- Use `log/slog` exclusively. No `log` or `fmt.Print`.
- Use **constant-based log keys** defined at the top of each file:
  ```go
  const (
      logKeyError         = "error"
      logKeyMessageID     = "message_id"
      logKeyCorrelationID = "correlation_id"
      logKeyResult        = "result"
  )
  ```
- Use structured attributes, not formatted strings:
  ```go
  s.logger.LogAttrs(ctx, lvl, logMsgProcessMessageDone,
      slog.String(logKeyResult, string(res)),
      slog.String(logKeyMessageID, req.MessageID),
      slog.Any(logKeyError, err),
  )
  ```
- Log levels: `Debug` for routine filtering, `Warn` for operational issues, `Error` for failures.

### 1.7 Observability (OpenTelemetry)
- **Mandatory** on every significant operation: tracing span + metric instruments.
- Span naming: `<package>.<Operation>` — e.g., `service.ProcessMessage`, `service.SolacePublish`, `api.dispatch`.
- Trace attributes: defined as constants with `traceAttr` prefix.
- Span events for key milestones: `message_filtered`, `solace_publish_success`, `archive_publish_success`.
- Metrics: counters for received/filtered/forwarded, histograms for processing duration.
- Record errors on spans: `gtrace.RecordError(span, err)` when an operation fails.

### 1.8 Testing
- **Table-driven tests** as the default pattern:
  ```go
  tests := []struct {
      name          string
      req           ProcessRequest
      setupMocks    func(s *MockSolacePublisher, a *MockArchivePublisher)
      expectedError error
  }{
      { name: "successful processing", ... },
  }
  for _, tt := range tests {
      t.Run(tt.name, func(t *testing.T) { ... })
  }
  ```
- **testify** for assertions: `assert.ErrorIs`, `assert.NoError`, `require.NoError`.
- **mockery** for mock generation (configured in `.mockery.yaml`).
- **Discarding logger** for unit tests:
  ```go
  slog.New(slog.NewTextHandler(io.Discard, nil))
  ```
- **In-memory metrics reader** for metrics testing.
- **`t.Parallel()`** where tests are independent.
- **Integration tests**: use `testify/suite` and `testcontainers-go` for real dependencies.

### 1.9 Concurrency
- **errgroup** (`golang.org/x/sync/errgroup`) for goroutine management.
- **signal.NotifyContext** for graceful shutdown (SIGTERM, SIGINT).
- No naked goroutines — every goroutine must have a supervisor (errgroup or WaitGroup).
- Context-based cancellation for all long-running operations.

### 1.10 Dependency Injection
- Constructor-based DI only. No global state, no init() side effects.
- Interfaces defined at the **consumer site**, not the producer site:
  ```go
  // service.go defines what it needs
  type SolacePublisher interface {
      Publish(ctx context.Context, country, msgID, correlationID string, payload any) error
  }
  ```
- Composition root in `pkg/app.go` or equivalent: wire everything together once.
- Components receive only the dependencies they need — not the entire config object.

### 1.11 Handler Pattern
- Handlers are thin: parse request → call service → map response/error.
- No business logic in handlers. Delegate everything to the service layer.
- Handler interface for pluggability:
  ```go
  type Handler interface {
      Handle(ctx context.Context, msg pubsub.Message) error
  }
  ```

### 1.12 Code Comments
- No comments that narrate *what* the code does (the code should be self-documenting).
- Comments explain *why* a decision was made or *why* something non-obvious exists.
- Exported types and functions should have doc comments when the purpose isn't obvious from the name.

## 2. Testing Standards

### 2.1 Unit Tests
- Table-driven tests (see §1.8 above).
- `t.Parallel()` for independent test cases.
- Mock all external dependencies (Solace, Pub/Sub, external APIs).
- Use `mock.MatchedBy` for argument matching in mock expectations.
- Helper functions for repetitive test setup (e.g., `newAttributes()`, `newFilterConfig()`).

### 2.4 Coverage Gate

**Minimum coverage: 30% per package (R1), rising to 60% (R3).**

- Enforced in CI via `go tool cover -func=coverage.out` check.
- Skippable with `[skip-test-check]` in commit message.
- New packages must include at least one test file in the introducing PR.
- See ADR-0006 for full policy and phase roadmap.

### 2.2 Integration Tests
- `testify/suite` for organizing integration test suites.
- `testcontainers-go` for real dependency containers.
- Test the full data flow end-to-end.

### 2.3 Mock Generation
- Configured via `.mockery.yaml` at the service root.
- Mocks output to a top-level `mocks/` directory mirroring the package structure.
- Regenerate mocks when interfaces change.

## 4. Enforcement & Cross-Communication

When any agent generates or reviews code, it **MUST**:

1. **Load this document** (`CODING_STANDARDS.md`) at the start of its run.
2. **Check each file** against the relevant sections before emitting output.
3. **Cite violations** by section number (e.g., §1.3 — import ordering wrong, §1.6 — non-slog logging used).
4. **Cross-reference**: if a violation spans multiple agent domains (e.g., backend-engineer produces unclear naming + docs-writer needs to document it), the reviewing agent MUST flag it and reference the agent responsible for remediation.
5. **No silent compliance** — if standards pass, state explicitly: "All artifacts comply with CODING_STANDARDS.md §§1–3."

### Review Pipeline Standard Flow
```
code-reviewer starts:
  1. Load CODING_STANDARDS.md
  2. For each artifact file:
     - Check §1 (Go Code) for backend artifacts
     - Check §2 (Testing) for test artifacts
     - Check §3 (Documentation) for docs artifacts
  3. For each violation:
     - Record: file:line, section violated, evidence, agent responsible
     - If outside review domain: flag for cross-agent escalation
  4. Output: pass/fail with findings[]
```
